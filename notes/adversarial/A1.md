# A1

对象：`r1-package-map.md` 的 83 行名词表和「扩展点清单」，加上 `r1-docs-nouns.md`。两份 sha256 与本轮给定值一致。下面每条只攻击地图过厚或过空。

## A1-01 Environment 与 sandbox 挤在同一条轴上

- 攻击：扩展点清单的轴名只有 Environment。这一轴同时装着任务目录 `environment/`、task.toml 的 EnvironmentConfig、运行时的 EnvironmentType。Sandbox 没有自己的轴，只充当 EnvironmentType 的换词。文档名词另开 Sandbox、Environment（运行时类型）、`BaseEnvironment` 三条，定义互相指向。这是同义词轮换：目录、资源段、sandbox 实现被换成三个词，读者会当成三条接入轴。改法：目录固定写 `environment/`，运行时固定写 sandbox。
- 证据：`r1-package-map.md` 名词表 EnvironmentConfig：「task 侧 [environment]：资源与镜像，不是 provider 类型。」EnvironmentType：「运行时 sandbox 枚举，不是 task.toml 字段。」`environment/`：「题目环境目录，is_valid_dir 要求该目录存在；里面放镜像定义，不在这里选择 docker 还是 singularity。」扩展点：「Environment。选择键在 trial 或 job 的 environment.type，不在 task.toml。」`r1-docs-nouns.md` Sandbox：「跑 task 的隔离环境；文档写明 CLI `--env`/`-e` 和 job config `environment.type` 把 sandbox 叫成 environment。」同文件：「sandbox 与 environment：task 目录里有 `environment/`；CLI 的 environment 又是 sandbox 实现。同一页承认这个名字不好。一个 task 目录看不出跑在哪个 sandbox。」Task 的两句官方定义是：「一条或多条 instruction、一个 sandbox environment，外加一个 verifier」；以及「an instruction, environment, and test script」。
- 若主协调不改，会误导读者做什么：读者把「接 environment」当成一件事。只交 `environment/Dockerfile`，或只改 `environment.type`。任务目录看不出 sandbox，运行时 type 也看不出镜像文件齐不齐。

## A1-02 BaseEnvironment 的方法名单有两套

- 攻击：同一个 `BaseEnvironment`，包地图把文件传输收成 `upload`、`download`，文档名词写成 `upload_file`、`upload_dir`、`download_file`、`download_dir`。文档名单里没有 `type`，包地图名单里有 `type`。自定义 sandbox 的接口在地图里过厚，厚成了两份契约。
- 证据：`r1-package-map.md`：「BaseEnvironment | 自定义 sandbox 要实现的抽象：type、start、stop、upload、download、exec。| environments/base.py」。`r1-docs-nouns.md`：「Environment（运行时类型）：一个 `BaseEnvironment` 实现，方法是 `exec`、`upload_file`、`upload_dir`、`download_file`、`download_dir`、`start`、`stop`。」出处 `https://docs.harborframework.com/core-concepts/tasks/environment`。另一条把 `BaseEnvironment` 再定义成「自定义 sandbox 要实现的接口」，出处 `…/sandboxes/custom-sandboxes`。包地图不确定点：「Agent 与 Environment 的 import_path 不检查基类；错误类会在调用时失败，失败形态依赖该类缺什么方法：unknown」。
- 若主协调不改，会误导读者做什么：按包地图实现的类会交 `upload` / `download`。按文档实现的类会交四套文件方法并漏掉 `type`。失败被笔记留在 unknown，读者要等到构造 trial 才知道缺的是哪一个方法。

## A1-03 文档站无版本，schema_version 一行里叠了多套数字

- 攻击：文档名词开头写明文档站不能当成 0.23.0 定论，后面的官方用词仍和包地图的 0.23.0 名词表接在同一张图上，多数条目没有逐条标「无版本文档」。`schema_version` 这一行同时写下 TaskConfig 默认 `"1.4"` 和 DatasetManifest、CompileConfig、ExecConfig 默认 `"1.0"`，接入列是「可省略」。文档字段参考示例是 `"1.3"`，创建教程写 `version = "1.0"`。包不枚举校验。template-adapter 的 task.toml 写 1.0，笔记把「1.0 会不会被拒绝」标成 unknown。教程的 `[metadata] author_name` 在包地图 PackageInfo 里没有这一字段，PackageInfo 写的是 `[task]` 的 `authors`。
- 证据：`r1-docs-nouns.md`：「文档站未标版本，不能当成 0.23.0 定论。」「`schema_version`：task configuration format 的版本；字段参考页示例是 `"1.3"`。」「创建教程示例写 `version = "1.0"` 和 `[metadata] author_name`；configuration 参考写 `schema_version = "1.3"` 和 `[task] authors`。」「tag 上的 `CHANGELOG.md` 开头仍是多段 `Unreleased`，没有 `## 0.23.0` 标题。」`r1-package-map.md`：「schema_version | TaskConfig 默认 "1.4"；DatasetManifest、CompileConfig、ExecConfig 默认 "1.0"。| models/task/config.py | 可省略」。「TaskConfig | …schema_version 默认字符串 "1.4"，旧键 version 会改名为 schema_version；本安装没有枚举校验。」不确定点：「template-task 写 1.4，template-adapter 的 task.toml 写 1.0。…1.0 模板在 0.23.0 运行时是否被别处拒绝：unknown。」PackageInfo：「出现时 name 必填且为 org/name，version、description、authors、keywords 可选。」
- 若主协调不改，会误导读者做什么：转化脚本会写入 `"1.3"` 或 `version = "1.0"`，并把它当成 0.23.0 的格式版本。留空则落到包默认 `"1.4"`，和教程、adapter 模板、文档参考三处都不同。dataset.toml 会误用任务的 `"1.4"`，或任务误用数据集的 `"1.0"`。`author_name` 会按教程写进一段 PackageInfo 没有的表。

## A1-06 pip extra 的名字是 adapter，装的不是 Adapter

- 攻击：tag 上的 optional extra `adapter` 依赖 `claude-agent-sdk`。名词表里的 Adapter 是 `cli/adapters.py` 的生成期脚手架。包地图 83 行和扩展点清单都没有这个 extra。云 sandbox 的「提示 pip extra」也没有写出 extra 名。DockerEnvironment 行的「registry 项」容易和名词表的 Registry、`registry.json` 读成同一个 registry。
- 证据：`r1-docs-nouns.md`：「同名但不是上面那个 Adapter：该 tag 的 `pyproject.toml` 有 optional extra `adapter = ["claude-agent-sdk>=0.1.17"]`。」出处 `https://raw.githubusercontent.com/harbor-framework/harbor/v0.23.0/pyproject.toml`。`r1-package-map.md`：「Adapter | CLI 子命令 harbor adapter 的生成期脚手架，不是运行时插件；…| cli/adapters.py | adapter 作者在生成任务时提供，运行 job 不加载它」。扩展点 Environment：「云类型缺依赖时 ImportError，并提示 pip extra。」「DockerEnvironment | EnvironmentType.DOCKER 的实现，registry 项无额外 pip extra。| environments/docker/docker.py」。Registry 行：「registry.json 的模型」。
- 若主协调不改，会误导读者做什么：读者执行 `pip install 'harbor[adapter]'`，以为装上了把上游题写成 Harbor 目录的脚手架，得到的是 `claude-agent-sdk`。选 daytona、e2b、modal 这类 type 时会把这个 extra 再装一次，或认为登记进 `registry.json` 就不必装云依赖。

## A1-07 Adapter 占着扩展点章节，job 不加载它

- 攻击：扩展点清单把 Adapter 与 Agent、Environment、Verifier、Metric 排成同一级。正文写运行 job 不 import 这个类。TemplateAdapter 约定 `run()` 把上游题写成 task 目录，wizard 按 adapter id 改类名。`review` 会找 `scripts/validate_adapter.py`，本安装的 site-packages 里没有该脚本，找不到只警告。文档侧「新 benchmark」写明没有 adapter 页，邻近做法是做 dataset。地图把一条不进运行时的生成脚手架做成了轴，dataset 那条真路径反而写在另一份笔记里。
- 证据：`r1-package-map.md` 扩展点顺序含 Agent、Environment、Verifier、Agent protocol、Adapter、Metric。「Adapter。不是运行时扩展点。入口：cli/main.py 的 harbor adapter」。init 复制的文件包括 `adapter.py.tmpl`、`parity_experiment.json`。「运行 job 不 import 这个类。」「找不到只警告。」TemplateAdapter：「约定 run() 把上游题写成 Harbor task 目录」。`r1-docs-nouns.md`：「文档站没有名为「接一个新 benchmark」的步骤，也没有 adapter 页。」邻近做法是 `harbor run -p`、`dataset.toml`、`harbor publish`。模板还要求把任务上传到 `https://github.com/laude-institute/harbor-datasets` 并改那份 `registry.json`，笔记写明那是 GitHub 模板说明，不是当前文档站步骤。
- 若主协调不改，会误导读者做什么：读者实现 `adapter.py` 的 `run()`，再跑 job，期望 Harbor 加载这个类。job 不读它。`review` 只给警告时会被当成脚手架已经接进运行时。parity 和 `harbor-datasets` 的 `registry.json` 会被当成 job 的必经门。

## A1-08 ACPAgentMixin 和 `acp:` 注册表简写是两扇门

- 攻击：文档里的 ACP 接入是 `acp:<agent_id>`，从 ACP Registry 安装，并在 task environment 里运行。包地图的 Agent protocol 轴是继承 `ACPAgentMixin`、实现 `acp_command`，BridgeKind 只有 `acp`。Agent 节只用半句把「ACP registry 简写」从 `import_path` 里排除出去，没有写这个简写要装什么、跑在哪。缺 mixin 时笔记写普通 `setup` 加 `run` 仍可跑。名字都叫 ACP，地图却只展开了 bridge 那一扇。
- 证据：`r1-docs-nouns.md`：「ACP：Agent Client Protocol；Harbor 的 `acp` 集成从 ACP Registry 安装并在 task environment 里运行 agent。」「已有安装包走预置名字，或 `acp:<agent_id>` / `acp:<agent_id>@<version>`。」`r1-package-map.md`：「ACPAgentMixin | agents/protocols 里唯一协议：acp_command，供 ACP bridge 把目标 agent 当 ACP server 拉起。」扩展点 Agent：「`--agent` 里含冒号且不是 ACP registry 简写时也走 import_path。」Agent protocol：「缺了 mixin 只是不能当 ACP bridge 的目标 agent，普通 setup 加 run 仍然可跑。」
- 若主协调不改，会误导读者做什么：读者继承 `ACPAgentMixin`，以为自己的类会以 `acp:<agent_id>` 出现在 ACP Registry 里，并在任务容器内被安装。另一路读者只写 `acp:某id`，不实现 `acp_command`，bridge 通道没有目标。
