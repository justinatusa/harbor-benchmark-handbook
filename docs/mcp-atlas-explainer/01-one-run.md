# 一道题怎么跑完

公开题库第一行，题号 `689f4d693e212e8ef3390731`，问的是某款开源游戏：仓库哪一年建的，官网域名哪一年注册的，两个年份差多少。助手要自己去查仓库、查网页、查域名，再减一次，写进回答。题面没有写下 `github_search_repositories` 这种工具 id。2026-09-27 对公开的 500 行做过同样的检查：把该行允许使用的工具 id 拿去在题面里搜索，500 行都没有命中。题面里仍可能出现 GitHub 这种普通词。那次搜索只检查工具 id。

官方 README 的第一句把整件事说成：在一个可复现的 Docker 沙箱里，用真实的 MCP server 看智能体会不会用工具，并用另一个语言模型打分。这种打分叫 LLM-as-judge，再请一个模型看回答盖住了多少条事实，不做字符串完全相等。

## 题放在一行里

论文（arXiv 2602.00933）写的全量是 1,000 道题：公开一半，另一半不随数据集发布。Hugging Face 上的 `ScaleAI/MCP-Atlas` 是公开的那一半。2026-09-27 读那份 parquet，行数是 500。`run_eval.py` 不传 `--input` 时加载的就是这一份。未发布的那一半不在这个 parquet 里。默认脚本读到的 500 行就是公开集的全部。

一行五个字段。`TASK` 是题号，公开 500 行都是 24 个字符。`PROMPT` 是题面。`ENABLED_TOOLS` 是这一题允许模型看见的工具名。`GTFA_CLAIMS` 是回答里应该出现的事实句。`TRAJECTORY` 是一条够用的调用记录，含工具名、参数和当时返回的内容。

批量脚本只把题面和允许的工具名送给模型。事实句留给评分。调用记录留着事后对照。评分看事实句盖住多少，不要求模型走出和记录同一条路径。

## 从脚本走到子进程

sandbox 是 `services/agent-environment/` 里的那只容器。镜像起来之后，一个进程在端口 1984 上提供网页接口。真正搜仓库、读文件的，是它再拉起的 MCP server。一个 server 是一个单独的程序。当前模板 `mcp_server_template.json` 有 36 条启动命令，README 和论文也写 36 个 server。一只镜像里挂着这批程序。模型不会一次看见它们公布的全部动作，下一页讲短名单怎么裁。

harness 是 `services/agent-harness/` 里的 TypeScript 循环，跑在宿主机上，默认听 3001，不在沙箱容器里。变更记录把这次从 Python 改写成 TypeScript 的那一节标成 v2.0.0。旧的 Python 循环目录已经从公开提交里删掉。v2.0.0 是这一节的标题。镜像标签是另一套编号，跑的时候对的是 `1.2.7`，见 [04-versions-and-running.md](04-versions-and-running.md)。

```text
被测模型
  ^  对话接口，地址在 LLM_BASE_URL
  v
run_eval.py  把一题交给循环
  v
harness，宿主机进程，默认端口 3001
  |  向沙箱要工具列表，再提交一次工具调用
  v
sandbox，容器里的网页服务，端口 1984
  |  用标准输入输出交给本机子进程
  v
MCP server（npx 或 uvx 拉起的程序）
  |
  v
有的只读容器里的文件，有的再去访问外部网站
```

`run_eval.py` 把一题 POST 到 harness 的 `/v2/mcp_eval/run_agent`，默认地址是 `http://localhost:3001`。请求里有题号、题面、这一题允许的工具名、被测模型名，以及镜像名。这份公开客户端不会因为请求里写了镜像名就当场执行 `docker run`。容器要先启动。客户端实际使用的沙箱地址只有 `MCP_SANDBOX_URL`。

循环按 OpenAI 对话接口去问被测模型，地址来自 `LLM_BASE_URL`。它先访问沙箱的 `/list-tools`。请求里如果带了 `enabledTools`，就只留下这些名字，再交给模型。模型返回一次工具调用，循环把工具名和参数 POST 到沙箱的 `/call-tool`。沙箱地址默认 `http://localhost:1984`。Makefile 把容器的 1984 映到本机的 1984。结果塞回对话，再问模型。模型不再调用工具时，循环结束。最后那段文字就是交去评分的回答。

沙箱这个网页服务自己不搜仓库，也不读文件。它把调用交给本机的 MCP 客户端。客户端按模板里的命令启动子进程，用标准输入输出跟子进程说话。slack 的启动参数里写了 `--transport stdio`，stdio 就是这种本机传输。端口 1984 上的路径是沙箱自己的 `/list-tools`、`/call-tool`、`/enabled-servers`、`/health`。

子进程拿到调用之后，有的只碰容器里的 `/data`，例如读文件、跑计算。有的会再访问外部网站，例如搜索和查仓库。被测模型只和 harness 对话。题面停在交给模型的那条消息里。Brave、GitHub、Notion 上的请求如果发生，发生在对应的 MCP 子进程里面。

两个开关都带 enable，各管一层。`ENABLED_SERVERS` 决定哪些程序会启动。`ENABLED_TOOLS` 决定这一题让模型看见哪些动作。容器可以挂着很多 server。名单里多写一个沙箱没加载的名字，模型看不见。沙箱加载了、名单里没有的动作，模型也看不见。

README 写，一道题的全部工具调用要打到同一个沙箱。filesystem、memory、git、MongoDB 假定这一题内部看到的是同一份文件和数据。按每一次调用分到不同容器，这些工具会对不上。

公开的这份循环不在题和题之间重置沙箱。源码写，不调用 `/reset-state`，因为镜像对这个路径返回 404。论文写他们评测时会在题之间重启容器，避免上一题的文件留到下一题。那是论文里的实验跑法。按公开 README 在本机跑，默认是一只容器一直开着。

被测模型和 judge 都在容器外面。沙箱镜像基于 Python 3.12 的瘦镜像，构建文件里没有安装显卡驱动的步骤。模型服务如果自己要用显卡，那是 `LLM_BASE_URL` 那一头的事。

## 分数看事实句盖住多少

judge 是 `services/scoring/score_claims.py` 里的另一次模型调用。它读最终回答和 `GTFA_CLAIMS`，不再把回答送回那些工具。每条事实句单独看：完全盖住、盖住一部分，或没盖住。一道题的覆盖率是这些分数的平均。

论文主分析把覆盖率达到 0.75 的题算通过。低于 0.75 才做失败归类。公开评分脚本同时输出两档，字段是 `pass_rate_0.50` 和 `pass_rate_0.75`。论文附录 G 另外还列了 0.90 这一档。0.75 量的是事实句覆盖。工具有没有调对，不在这个分数里。

代码里的默认评判模型名是 `gemini/gemini-3.1-pro-preview`，可以用 `--evaluator-model` 或环境变量 `EVAL_LLM_MODEL` 换掉。论文第 3.3 节那次正式实验用了三个评判模型，主评判是 Gemini 3.1 Pro Preview。本地默认值和那次三模型实验是两件分开的事。论文图 1 里最高的通过率是 82.2%，分母是 20 个模型、全量 1,000 题、主评判、覆盖率至少 0.75。这份说明没有重跑模型，也没有把这个百分数当成公开 500 的复现分。

论文说全量上每题事实句平均 4.7 条，范围 1 到 23。公开文件里，能用 Python `ast.literal_eval` 读成列表的有 499 行，条数均值 3.91，最小 1，最大 23。题 `689cd6f8522029b7ad7b1fe5` 的字符串在代码围栏处没有闭合，没有算进这 499 行。这 499 行用的是 `ast.literal_eval`，没有按严格 JSON 再解析一遍。

## 没通过时怎么归类

诊断是另一支脚本，在 `services/diagnostics/`。论文附录 E 写，归类标签不改通过与否。名字在变更记录和 `mcp_failure_taxonomy.py` 里是同一套，调用类 4 个，理解类 7 个。

调用类：

- `malformed_call`：工具选对了，参数错了。
- `wrong_tool`：选了一个解决不了这个子问题的工具，正确的工具当时看得到。
- `no_tool_use`：这题需要查外部信息，模型却直接用自己的知识作答。
- `err_recovery`：工具返回错误之后，模型原样重试、打转或者放弃。

理解类：

- `task_misunderstanding`：答成了另一个问题，或漏了题面里的要求。
- `faulty_synthesis`：工具返回是对的，组合或解释错了。
- `response_misparsing`：返回的结构读错了，或抽错了字段。
- `early_termination`：题意懂了，没做完就停。
- `hallucinated_fact`：回答里写出了任何工具输出都没出现的内容。
- `logical_error`：拿到的数据是对的，多步推理错了。
- `constraint_violation`：忽略了题面里写明的条件。

出题时还用过一份更粗的三步核对：工具选得对不对、参数对不对、结果读得对不对。论文附录 D.3 写，那份三步核对和这 11 类各记各的。

上面这道游戏题的短名单有 15 个名字，参考解法只用了其中 5 个。模型为什么看不见目录里的其他动作，下一页拆开。
